# ADR-008 — SQL migrations without a framework

**Status:** Accepted · **Date:** 2026-09-14 · **Build:** 0.1 (M1)

## Context

Two stores need schema management, and they are not alike. PostgreSQL holds
transactional state with transactional DDL (ADR-003); ClickHouse holds
analytical event history, has no transactional DDL, no primary-key uniqueness,
and a different type system (ADR-002).

The requirement that shapes this is reproducibility. A backtest result must
reference the exact dataset and schema it ran against (Phase 4 §43,
Build 0.1 Rev.1 §39), which is impossible if two environments can claim the
same schema version while differing.

## Decision

Numbered `.sql` files per store, applied in order by a small runner
(`libs/storage/migrations.py`), with the SHA-256 of each file recorded in a
`schema_migrations` ledger table as applied.

Four rules the runner enforces:

1. **An applied migration that has changed is refused.** Editing one produces
   environments whose schemas differ while both report the same version. The
   remedy is a new migration, and the error message says so.
2. **A deleted applied migration is refused.** The ledger would then describe a
   schema that cannot be reproduced from the repository.
3. **Version numbers must be contiguous from 001, with no duplicates.** A gap is
   ambiguous about whether a migration was lost, and the order of schema changes
   is not something to resolve by guessing.
4. **Application stops at the first failure.** A later migration may depend on
   an earlier one.

The runner reaches its store through two injected callables — execute one
statement, list applied versions — so it carries no database dependency and is
fully tested without one. Each store supplies its own pair
(`libs/storage/postgres.py`, `libs/storage/clickhouse.py`).

## Alternatives rejected

**Alembic.** The standard choice, with autogeneration and downgrades. Rejected
on fit: it is built around SQLAlchemy and PostgreSQL, so ClickHouse would need a
second mechanism anyway — and two migration systems with different guarantees is
worse than one simple system with the same guarantees for both.

**Autogenerated migrations from an ORM.** Rejected with the ORM itself: these
schemas are deliberately hand-written. `market_events` chooses `Decimal64(8)`
over float because a float cannot hold a venue tick exactly, `DateTime64(9)`
because nanosecond precision is what a fast-decaying signal is measured with,
and its `ORDER BY` to match the dominant research query. An autogenerator would
not make those choices, and they are not incidental.

**Down-migrations.** Rejected: a reversal of a data-carrying schema change is
rarely correct and encourages treating an applied migration as editable, which
rule 1 exists to prevent. Recovery is a corrective forward migration.

**No checksums.** Rejected: without them the divergence in rule 1 is invisible
until it surfaces as a confusing data defect.

## Consequences

- Migrations are written by hand, which is the intent for a schema where the
  column types carry research meaning.
- A mistake in an applied migration is corrected forward, never edited.
- ClickHouse DDL is not transactional, so a failed migration there can leave a
  partially created object; the runner stops rather than continuing, and the fix
  is a forward migration.
- Statement splitting is a small hand-written scanner, because ClickHouse's HTTP
  interface takes one statement per request. It handles line comments and single-
  quoted strings, which is sufficient for files we control, and is covered by
  tests including the semicolon-inside-a-string case.

## Revisit when

A third store arrives whose DDL this cannot express, or migration volume makes
hand-writing them the bottleneck rather than the safeguard.
